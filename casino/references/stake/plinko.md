## 1. Random number generation (Stake's published implementation)

Source: `https://stake.com/provably-fair/implementation`
(archived: `https://web.archive.org/web/20250324083758/https://stake.com/provably-fair/implementation`)

> For each verifiable bet, a client seed, a server seed, a nonce and a cursor are used as
> the input parameters for the random number generation function. This function utilises
> the cryptographic hash function HMAC_SHA256 to generate bytes which are then used as
> the foundation for how we generate provably fair random outcomes on our platform.

```js
// Random number generation based on following inputs: serverSeed, clientSeed, nonce and cursor
function byteGenerator({ serverSeed, clientSeed, nonce, cursor }) {
  // Setup curser variables
  let currentRound = Math.floor(cursor / 32);
  let currentRoundCursor = cursor;
  currentRoundCursor -= currentRound * 32;

  // Generate outputs until cursor requirement fullfilled
  while (true) {
    // HMAC function used to output provided inputs into bytes
    const hmac = createHmac('sha256', serverSeed);
    hmac.update(`${clientSeed}:${nonce}:${currentRound}`);
    const buffer = hmac.digest();

    // Update curser for next iteration of loop
    while (currentRoundCursor < 32) {
      yield Number(buffer[currentRoundCursor]);
      currentRoundCursor += 1;
    }
    currentRoundCursor = 0;
    currentRound += 1;
  }
}
```

Published details on the inputs (same page):

- **Server Seed** — "generated by our system as a random 64-character hex string. You are
  then provided with an encrypted hash of that generated server seed before you place any
  bets. … To reveal the server seed from its hashed version, the seed must be rotated by
  the player, which triggers the replacement with a newly generated one."
- **Client Seed** — "belongs to the player and is used to ensure they have influence on
  the randomness of the outcomes generated. … During registration, a client seed is
  created for you by your browser."
- **Nonce** — "simply a number that increments as every new bet is made."
- **Cursor (Incremental Number)** — "We use 4 bytes of data to generate a single game
  result, and because SHA256 is limited to 32 bytes, we utilise this implementation of a
  cursor … The cursor is only iterated over when the game being played requires the
  generation of more than 8 (32 bytes / 4 bytes) possible outcomes. … The cursor starts
  as 0 and gets increased by 1 every time the 32 bytes are returned by the HMAC_SHA256
  function."
- From the page's list "Games with more than 1 incremental number":
  **"Plinko (2 increments per game to cover possible 16 decisions)"**
  (i.e. cursor rounds 0–1 yield up to 16 four-byte floats — one per row of pins).

## 2. Bytes → floats (Stake's published conversion)

Source: `https://stake.com/provably-fair/conversions`
(archived: `https://web.archive.org/web/20231204093753/https://stake.com/provably-fair/conversions`)

> The output of the Random Number Generator (byteGenerator) function is a hexadecimal
> 32-byte hash. As explained under the cursor implementation, we use 4 bytes of data to
> generate a single game result. Each set of 4 bytes are used to generate floats between
> 0 and 1 (4 bytes are used instead of one to ensure a higher level of precision when
> generating the float.)

```js
// Convert the hash output from the rng byteGenerator to floats
function generateFloats ({ serverSeed, clientSeed, nonce, cursor, count }) {
  // Random number generator function
  const rng = byteGenerator({ serverSeed, clientSeed, nonce, cursor });
  // Declare bytes as empty array
  const bytes = [];

  // Populate bytes array with sets of 4 from RNG output
  while (bytes.length < count * 4) {
    bytes.push(rng.next().value);
  }

  // Return bytes as floats using lodash reduce function
  return _.chunk(bytes, 4).map(bytesChunk =>
    bytesChunk.reduce((result, value, i) => {
      const divider = 256 ** (i + 1);
      const partialResult = value / divider;
      return result + partialResult;
    }, 0)
  );
};
```

Equivalently: `float = b0/256 + b1/256² + b2/256³ + b3/256⁴`, giving a value in [0, 1).

## 3. Plinko game-event translation (Stake's published math)

Source: `https://stake.com/provably-fair/game-events`
(archived: `https://web.archive.org/web/20231204091959/https://stake.com/provably-fair/game-events`)

Verbatim:

> **Plinko**
> For any game of Plinko, the generated outcome is based on the path of the falling ball.
> The game event determines the direction of the falling ball for each level in the
> falling process. Players can choose between 8 and 16 pins of play, which determines the
> number of game events required to generate a complete path from top to bottom. Since
> there are only two possible directions (left or right) the translation is done by
> multiplying each float by 2, which maps to the following index:

```js
// Index of 0 to 1 : left to right
const DIRECTIONS = [ left, right ];

// Game event translation
const direction = CARDS[Math.floor(float * 2)];
```

(Note: the `CARDS[...]` identifier is a typo in Stake's own published snippet — the
index defined immediately above it is `DIRECTIONS`; the intended lookup is
`DIRECTIONS[Math.floor(float * 2)]`.)

Putting the published pieces together, one Plinko drop with `rows` pins (8–16) consumes
`rows` floats (cursor spans 2 HMAC rounds when rows > 8):

1. `floats = generateFloats({ serverSeed, clientSeed, nonce, cursor: 0, count: rows })`
2. For each float: `direction = floor(float * 2)` → `0 = left`, `1 = right`.
3. The sequence of left/right decisions is the ball's path; the landing pocket follows
   from the path (a board with `rows` rows has `rows + 1` pockets, indexed 0..rows from
   far left to far right; the landing index equals the count of `right` events —
   this last mapping is the standard consequence of the published path mechanics, the
   pages above publish the per-row direction math verbatim).

### How the client obtains the multiplier table (from Stake's published client code)

Stake's own shipped Plinko frontend chunk (archived:
`https://web.archive.org/web/20220106192523js_/https://stake.com/_app/chunks/game-daf90b51.js`)
shows the pocket multipliers are **served by Stake's API, keyed by risk and rows**, via
this GraphQL query (reconstructed from the archived document AST in that file):

```graphql
query PlinkoPayouts {
  info {
    plinkoPayouts {
      payouts
      rows
      risk
    }
  }
}
```

The same archived chunk contains Stake's client-side binomial helper used to display
pocket probabilities (Pascal's triangle over `rows` coin-flips):

```js
const probabilities = e => {
  let t = [1];
  for (let s = 0; s < e; s += 1) {
    const n = [];
    for (let a = 0; a <= t.length; a += 1)
      n.push(.5 * ((t[a - 1] || 0) + (t[a] || 0)));
    t = n;
  }
  return t;
};
```

i.e. `P(pocket k | rows n) = C(n, k) / 2^n`. Defaults in the same chunk: risk = `medium`,
rows = `16`.

### Completeness caveat — full per-pocket grid

Stake does **not** statically publish the pocket-by-pocket multiplier arrays (27
risk×rows combinations × 9–17 pockets each) on any fairness, help, or blog page found in
stake.com / stake.us or their archives. Stake's own shipped client code (Section 3)
shows the full grid is delivered at runtime by the `PlinkoPayouts` GraphQL query
(`info.plinkoPayouts { payouts rows risk }`) and rendered on the game board. The tables
above (per risk/rows destination counts, minimum and maximum multipliers) are the
complete set of numeric payout tables Stake publishes as page content. Any
pocket-by-pocket listing found elsewhere is third-party transcription of the API data
and is deliberately not reproduced here; to capture the full grid payout-for-payout from
Stake itself, query `PlinkoPayouts` against Stake's GraphQL API from a non-blocked
network, or read the multipliers off the live game board per risk/rows setting.

## 5. House edge / RTP as published

- No Plinko-specific house-edge or RTP number appears on Stake's provably-fair pages,
  Plinko game pages, or Plinko blog posts captured above.
- Stake's fairness docs publish the house-edge convention for its Originals via the
  Limbo game-event code on the same game-events page: `// Game event translation with
  houseEdge of 0.99 (1%)` — i.e. Stake Originals are tuned to a 1% house edge.
- Stake's blog `casino-house-edge-guide` (archived
  `https://web.archive.org/web/20240910144335/https://stake.com/blog/casino-house-edge-guide`)
  states for the Stake Originals it covers: Crash — "its RTP of 99%"; Dice — "the
  massive 99% RTP of Dice"; "Stake Original Keno (99% RTP)". Plinko is named there as
  one of the games with "some of the best RTPs" without a printed number.
- Consistent with the above, the expected value of the runtime payout tables is 0.99
  (99% RTP / 1% house edge) for every risk/rows setting — this exact figure for Plinko
  is an inference from Stake's published 1%-edge convention, not a printed Plinko number.
